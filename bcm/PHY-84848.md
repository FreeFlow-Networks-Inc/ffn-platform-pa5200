# The BCM84848 behind the four RJ45 ports

Status: **still not answering MDIO.** What follows is what the vendor's own
binaries say about driving it, recovered with `tools/ffn_mipscall.py`, plus what
that rules in and out.

## The vendor's init sequence

`libpanbcm_cp.so`'s `bcm_copper_phy_initialize`, from
`libs/broadcom/pan_bcm_api/src/5200/cp/pan_bcm_84848.c` — a file of about 180
lines:

```
:73    sysconf_init()
:88    soc_phy_common_init()
:89    soc_phyctrl_software_init()
:92    sal_config_set("phy_ext_rom_boot", "0")
:108   pan_read_84848_register(...)
:114   pan_read_84848_register(...)
```

`pan_read_84848_register` and `pan_write_84848_register` are static functions in
`pan_bcm_api.c` (around line 4848, which is a coincidence). They take an SDK
`unit`, check the OCTEON model, and dispatch to a local helper — so the PHY is
reached **through the switch SDK**, not over a side channel.

## `phy_ext_rom_boot=0` is the interesting line

It is a standard SDK SOC property (`spn_PHY_EXT_ROM_BOOT`), and `phy84740.c`
prints exactly what it selects:

```c
phy_ext_rom_boot ? "SPI-ROM" : "MDIO_TO_RAM"
```

So `0` means *do not* assume the PHY self-boots from an external SPI ROM —
download the firmware to it over MDIO. That is the same shape as the fix that
unlocked every other port on this chip: a microcontroller that never starts
because nobody loaded its microcode (see `SERDES-FIRMWARE.md`).

What makes it notable is that the vendor sets it **at runtime**, with
`sal_config_set`, immediately before PHY init — not in `config.bcm`. Runtime
properties land in the same store, so the config file is an equivalent place to
put it, but it is not a line anyone would find by diffing configurations.

It is now in `../octeon/bcmagent/ffn-bcm-overrides.conf`.

## Our build already has the driver and the firmware

Checked, because "the driver is missing" was the obvious hypothesis and it is
wrong. In the current `bcm.user`:

```
BCM84848                                    (dev_name string)
0000000124635408 D bcm_84844_firmware
0000000124635400 D bcm_84844_firmware_size
```

and both `phy8481.o` and `phy8481_firmware.o` are built for `octeon-ffn`.

The 84848 does **not** have its own firmware blob — `phy8481.c:944` puts
84844/84846/84848 on one arm that selects `bcm_84844_firmware`, and sets
`PHYCTRL_MDIO_BCST`, so the download is an MDIO broadcast.

## Why `phy_ext_rom_boot` is necessary but cannot be sufficient

Firmware download happens inside the PHY driver, and the driver only runs once
the SDK has probed the PHY at its configured address and attached. Probing reads
the identifier registers, which on this family are hardware and answer whether or
not the microcontroller has ever run.

So MDIO silence does not indicate missing firmware. It indicates the part is
held in reset, or is not at the address/bus we are asking. Firmware is the step
*after* the one that is failing.

## Where the reset is not

Ruled out this round, so nobody repeats it:

- **Not in the CP's I2C writes.** Every `libi2c_write_cmd_byte` call in
  `libports.so` targets `0x22`, `0x23`, `0x24` (all on virtual bus 9) or an SFP
  module EEPROM at `0x50`. That is the SFP cage subsystem, not the RJ45s.
- **Not in CP userland CPLD code.** No CPLD symbols exist in `brdagent`,
  `libports.so`, `libasic.so`, `libfpga.so`, `libmgmt.so` or `libpanbcm_cp.so`.
  The CP's `pan-cpld@2,0` is reached, if at all, by something else —
  `cpld_wdt.ko` is a watchdog.

Remaining candidates: OCTEON GPIO (20 lines, now readable — see
`../octeon/gpio/README.md`), the MP-side CPLD (`tools/ffn_mpcpld.py` exists), or
a BCM chip GPIO.

## The board's I2C expander map, as a by-product

All three are on the vendor's virtual bus 9, configured at `gryphon_ports.c`
1885-1897. PCA9555 register numbering: 0/1 input, 2/3 output, 4/5 polarity
inversion, 6/7 configuration (1 = input).

| addr | configuration | role |
|------|---------------|------|
| 0x22 | regs 6,7 = 0xff — all 16 input; **regs 4,5 = 0xff — polarity inverted** | SFP module presence |
| 0x23 | reg 6 = outputs, reg 7 = 0xff input; reg 2 driven 0xff | SFP control (low byte drives) |
| 0x24 | regs 6,7 = 0xff — all 16 input | further status |

**This settles the presence polarity.** `0x22` has hardware polarity inversion
enabled on every bit, so `MOD_ABS` — which is active-low — is already inverted by
the time anyone reads it: **1 means present**. `gryphon_is_sfp_present` returns
`gryphon_read_sfp_state`'s value unmodified, and applies the same contract to its
GPIO branch, so the GPIO lines read the same way round. On the live board that
makes lines 2 and 5 populated and 7, 14, 15 empty.

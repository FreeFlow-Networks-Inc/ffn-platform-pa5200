# The BCM84848 behind the four RJ45 ports

Status: **found.** It was never on the switch's MDIO. It is on the OCTEON's own
SMI bus 0, at exactly the four addresses the vendor's binary names, and it
responds.

```
ffn_mdio: 8001180000003800 addr 16 devad 1 ID = ffff.a040   <- a vendor RJ45 PHY address
ffn_mdio: 8001180000003800 addr 17 devad 1 ID = ffff.a040   <- a vendor RJ45 PHY address
ffn_mdio: 8001180000003800 addr 18 devad 1 ID = ffff.a040   <- a vendor RJ45 PHY address
ffn_mdio: 8001180000003800 addr 19 devad 1 ID = ffff.a040   <- a vendor RJ45 PHY address
```

Controls: addresses 5, 15, 20 and 25 on the same bus return `ffff.ffff`, and the
second SMI bus (`...3880`) returns `ffff.ffff` at every address. So this is four
devices at four specific addresses, not a bus that answers everything.

**It is not yet identified**, and the difference matters — see "what is not
established" below.

## Why every previous probe missed it

Every earlier attempt drove the BCM88375's external MDIO — all eight of its
buses, all four addresses — and got silence. That was the wrong controller.
`pan_read_84848_register` in `libpanbcm_cp.so` dispatches to a helper built
entirely from `cvmx-mdio.h` and `cvmx-smix-defs.h`: `CVMX_SMIX_CLK`,
`CVMX_SMIX_WR_DAT`, `CVMX_SMIX_CMD`, reached through `cvmx_mdio_45_read()`.
Nothing in that path touches the switch.

The device tree had been showing this all along — `mdio@1180000003800` and
`mdio@1180000003880` are the OCTEON's two SMI controllers, `mdio_octeon` binds
both, and both register as `mii_bus`es. The hardware path was present and driven
the whole time.

What was missing was only enumeration. Those DT nodes have no child PHY nodes,
so `of_mdiobus_register()` falls back to scanning — and the default scan is
**clause 22**. A clause-45-only PHY does not answer clause 22, so nothing was
found and `/sys/bus/mdio_bus/devices` stayed empty, which looks exactly like "no
PHY there".

`octeon/kctl/ffn_mdio.c` does the clause-45 scan the kernel did not, on the bus
the kernel already registered. Read-only: `mdiobus_c45_read()` holds the bus
lock, and there is no write path in it at all.

## This means the SDK can never drive this PHY

The four `port_phy_addr_xe*` overrides point the SDK at addresses 0x10-0x13 on
**its own** MDIO, and the PHY is not there. The SDK reaches external PHYs through
the CMIC; it has no route to a device on the OCTEON's SMI. The vendor's own code
reflects that split — it uses the SDK's phy control layer for bookkeeping
(`soc_phyctrl_software_init`) but does every actual register access over OCTEON
MDIO.

So an own-code 84848 driver is not an optimisation over using the SDK. It is the
only route.

## What is NOT established

The identifier does not decode to a BCM84848, and the reads are not fully
trustworthy yet:

- `DEVID1` (register 2) reads `0xffff` at every address and every device
  address. A real clause-45 identifier would not.
- `DEVID2` (register 3) returns a real-looking value, but **it is not stable
  across runs**: address 16 read `a040` five times running in one batch, then
  `84f9` in the next. Within a run it repeats; between runs it changes, and it
  also changes with `devad` in a way a package identifier should not.
- Decoding `a040` gives model `0x04`. `PHY_BCM84848_MODEL` is `0x0F`
  (`phyident.h:402`).

The Linux driver is not the problem: `cavium_mdiobus_set_mode()` sets
`smi_clk.s.mode = 1` and `preamble = 1` for C45, and `cavium_mdiobus_c45_addr()`
issues the same address cycle as `cvmx_mdio_45_read`. The frames are being
formed correctly.

The pattern — the PHY acknowledges at exactly the right addresses but returns
data that varies between reads — is what you get from a device that is powered
and decoding its address but not driving valid data back. Two candidates worth
testing next, in order:

1. **MDIO clock/sampling.** `SMI_CLK` also carries `phase` and `sample`, which
   the Linux driver leaves at its own defaults. If the bus is clocked faster
   than this PHY tolerates, the address phase still works while the data is
   sampled at the wrong instant — which would produce exactly this.
2. **The part is held in reset**, powered enough to ACK but not to respond.

Do not put an identification in any commit message or config comment until one
of those is settled.

## The vendor's init sequence

`libpanbcm_cp.so`'s `bcm_copper_phy_initialize`, from
`libs/broadcom/pan_bcm_api/src/5200/cp/pan_bcm_84848.c` — a file of about 180
lines:

```
:73    sysconf_init()
:88    soc_phy_common_init()
:89    soc_phyctrl_software_init()
:92    sal_config_set("phy_ext_rom_boot", "0")
:108   pan_read_84848_register(...)
:114   pan_read_84848_register(...)
```

`pan_read_84848_register` and `pan_write_84848_register` are static functions in
`pan_bcm_api.c` (around line 4848, which is a coincidence). They take an SDK
`unit`, check the OCTEON model, and dispatch to a local helper — so the PHY is
reached **through the switch SDK**, not over a side channel.

## `phy_ext_rom_boot=0` is the interesting line

It is a standard SDK SOC property (`spn_PHY_EXT_ROM_BOOT`), and `phy84740.c`
prints exactly what it selects:

```c
phy_ext_rom_boot ? "SPI-ROM" : "MDIO_TO_RAM"
```

So `0` means *do not* assume the PHY self-boots from an external SPI ROM —
download the firmware to it over MDIO. That is the same shape as the fix that
unlocked every other port on this chip: a microcontroller that never starts
because nobody loaded its microcode (see `SERDES-FIRMWARE.md`).

What makes it notable is that the vendor sets it **at runtime**, with
`sal_config_set`, immediately before PHY init — not in `config.bcm`. Runtime
properties land in the same store, so the config file is an equivalent place to
put it, but it is not a line anyone would find by diffing configurations.

It is now in `../octeon/bcmagent/ffn-bcm-overrides.conf`.

## Our build already has the driver and the firmware

Checked, because "the driver is missing" was the obvious hypothesis and it is
wrong. In the current `bcm.user`:

```
BCM84848                                    (dev_name string)
0000000124635408 D bcm_84844_firmware
0000000124635400 D bcm_84844_firmware_size
```

and both `phy8481.o` and `phy8481_firmware.o` are built for `octeon-ffn`.

The 84848 does **not** have its own firmware blob — `phy8481.c:944` puts
84844/84846/84848 on one arm that selects `bcm_84844_firmware`, and sets
`PHYCTRL_MDIO_BCST`, so the download is an MDIO broadcast.

## Why `phy_ext_rom_boot` is necessary but cannot be sufficient

Firmware download happens inside the PHY driver, and the driver only runs once
the SDK has probed the PHY at its configured address and attached. Probing reads
the identifier registers, which on this family are hardware and answer whether or
not the microcontroller has ever run.

So MDIO silence does not indicate missing firmware. It indicates the part is
held in reset, or is not at the address/bus we are asking. Firmware is the step
*after* the one that is failing.

## Where the reset is not

Ruled out this round, so nobody repeats it:

- **Not in the CP's I2C writes.** Every `libi2c_write_cmd_byte` call in
  `libports.so` targets `0x22`, `0x23`, `0x24` (all on virtual bus 9) or an SFP
  module EEPROM at `0x50`. That is the SFP cage subsystem, not the RJ45s.
- **Not in CP userland CPLD code.** No CPLD symbols exist in `brdagent`,
  `libports.so`, `libasic.so`, `libfpga.so`, `libmgmt.so` or `libpanbcm_cp.so`.
  The CP's `pan-cpld@2,0` is reached, if at all, by something else —
  `cpld_wdt.ko` is a watchdog.

Remaining candidates: OCTEON GPIO (20 lines, now readable — see
`../octeon/gpio/README.md`), the MP-side CPLD (`tools/ffn_mpcpld.py` exists), or
a BCM chip GPIO.

## The board's I2C expander map, as a by-product

All three are on the vendor's virtual bus 9, configured at `gryphon_ports.c`
1885-1897. PCA9555 register numbering: 0/1 input, 2/3 output, 4/5 polarity
inversion, 6/7 configuration (1 = input).

| addr | configuration | role |
|------|---------------|------|
| 0x22 | regs 6,7 = 0xff — all 16 input; **regs 4,5 = 0xff — polarity inverted** | SFP module presence |
| 0x23 | reg 6 = outputs, reg 7 = 0xff input; reg 2 driven 0xff | SFP control (low byte drives) |
| 0x24 | regs 6,7 = 0xff — all 16 input | further status |

**This settles the presence polarity.** `0x22` has hardware polarity inversion
enabled on every bit, so `MOD_ABS` — which is active-low — is already inverted by
the time anyone reads it: **1 means present**. `gryphon_is_sfp_present` returns
`gryphon_read_sfp_state`'s value unmodified, and applies the same contract to its
GPIO branch, so the GPIO lines read the same way round. On the live board that
makes lines 2 and 5 populated and 7, 14, 15 empty.
